# ステップ3検証メモ（選手名簿照合の実装と検証）

実装日: 2026-11-18
実装: `src/mk8dx/roster.py`（検証ツール `tools/step3_check.py`、
テスト `tests/test_roster.py`、全48件合格）

## 実装したもの

ステップ2の申し送り「選手名簿照合（一括割り当て＋国旗併用＋
レース横断多数決）」を roster.py として実装した。

- エントリは (名前, 国旗) で識別。同名は国旗で区別し、国旗まで
  同じ場合は容量（最大同時出現数）を持つ1エントリにする
  （同名＝同タグ＝同チームなので集計に影響しない）。
- 割り当ては12行×選手名簿スロットの一括最適化（ハンガリアン法、
  自前実装。scipy の linear_sum_assignment と同一の割り当て・
  総コストになることを実データで確認）。
- 名前コストは重み付き編集距離: 記号（★◆◇☆と '*'）の欠落は安い、
  既知の混同ペア（ı/i、1/7、★/大、★/か 等）は安い、先頭文字の
  相違にはペナルティ。
- 国旗は「国名の同定」ではなく同一判定専用の署名で扱う
  （extract_flag_signature: 名前行右端の帯から背景色との差分で
  旗の矩形を切り出し、16x11に縮小）。実測の署名距離は
  同一国旗 0.084 / 異なる国旗 0.31 以上で、よく分離する。
  ハイライト行（黄色背景）でも背景中央色基準なので影響を受けない。
- 学習: 割り当てられた観測表記の多数決で正規名を更新、国旗署名を
  蓄積、容量は観測最大に更新。未割り当て行は仮登録し、2レースで
  再見したら本登録。低信頼の埋め合わせ割り当ては学習に使わない。

## 検証結果（ステップ2の実データ、2モード）

### モードA: 事前登録選手名簿＋closed（参加者＝選手名簿前提）

レース3 A / レース4 A / レース4 B の3画面すべてで **12/12名寄せに
成功し、2v2 クラスタリングが成立**した。内訳:

- 通常割り当てで決まった行: '日日-'（RR★の化け読み）も国旗ボーナス
  で正しく RR★(日本) に入った。
- 埋め合わせ（低信頼）になったのは各レース2〜3行で、いずれも
  目視確認と一致した。特にレース4 A の11・12行目は OCR が
  '三日'/'日日野' と完全崩壊していたが、目視では 11位=FR（日本旗）、
  12位=RR★（日本旗・ハイライト行）であり、埋め合わせの結果と一致。
- レース4 B の（名前, 累計）照合は 7/10＋RR★2名一致。不一致3件は
  いずれも累計数字のOCR側の問題（未読2件、37→97の誤読1件）で、
  名寄せの誤りではない。

### モードB: 選手名簿自動構築（open、レース1→3→4の順）

- レース1: 全行が新規候補（初回なので当然）。仮登録12件。
- レース3: 8/12 名寄せ成功。新規加入の2名（FR Flowx、A A）は
  正しく「新規」として検出された。
- レース4: 10/12 に収束（レース3で仮登録した新規2名が解決）。
- ただしレース1の誤読がそのまま仮登録される「幻エントリ」問題が
  残る: 'racist #7'（本当は #1 の誤読）、'三日'（FR の化け読みで
  日本旗を持つため、国旗が合う別人の行を吸着する）、'Rev' 等。
  これらが後続レースで誤割り当ての受け皿になる。
- 結論: 自動構築だけでは実戦投入は厳しい。**本命はモードA
  （管理画面から事前登録）で、自動構築は補助**（未登録選手の
  検出と候補提示）に位置づけるのが現実的。

## 検証中に見つけて直した問題

1. **国旗ペナルティの暴走**: 仮登録エントリの国旗は単一抽出由来で
   ノイズが多く、それを根拠にペナルティを課すと名前が完全一致する
   行まで弾かれた（'FR' が FR エントリに入れない等）。ペナルティは
   本登録エントリに限定し、ボーナスは常時適用に変更。
2. **正規名のドリフト**: OCRは '★' を系統的に落とすため、多数決では
   事前登録名まで 'RR★'→'RR' に流れた。事前登録名は固定（pinned）
   にし、多数決は自動構築エントリ専用にした。
3. **'*' の扱い**: en モデルは '★' を '*' と読む。コスト計算では
   記号として '★' と同一視する。

## 新しい発見

- **配信者は RR★（日本旗）本人**。ハイライト行（黄色）は常に
  配信者本人なので、「ハイライト行の検出＝特定プレイヤーの
  固定アンカー」として将来使える。ハイライト行は背景色が違うため
  OCRの読みが他行と系統的に異なる（'日日-' 等の化け読みは
  ハイライト行に集中している）ことも分かった。
- 最も難しいのは 'Xb◇ねえあまぁƄ' のような混植の長い名前で、
  どちらのモードでも直接割り当てでは決まらず、モードAでは
  埋め合わせで救済された。フレームを複数枚読んで多数決を取る
  実装（未着手）と組み合わせれば改善する見込み。
