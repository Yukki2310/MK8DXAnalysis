# ステップ1検証メモ（2026-11-18、実キャプチャ2枚で検証）

対象: ゴール順画面・累計順位画面 各1枚（1920×1080、CPUレースのためタグなし名前）

## 確定した事実

- リザルトは単一カラム12行構成（設計書の2カラム想定は誤り）。ROIは実測で校正済み
  （`config/roi_1080p.json`）。行は約76pxピッチで規則的に並ぶ。
- 2フェーズの判別: スコア列の `+` のOCR検出（上位行）＋スコア列の平均エッジ密度
  （実測: ゴール順画面 約0.070 / 累計画面 約0.031、閾値0.045）。2枚とも正しく判別できた。

## OCRの実測結果と方針変更

- **名前**: 生画像のままOCRするのが最良（信頼度0.9〜1.0）。二値化などの前処理を
  かけると逆に読めなくなる。12名中おおむね9〜10名が完全一致。誤りは
  小さいカナの混同（ッ/ツ、ィ/イ、ディ→デー、コ→ー）と、まれな先頭文字落ち。
  → 対策は「選手名簿方式」: 同じ12名が最大12レース走るため、レースをまたいだ
  多数決＋編集距離での名寄せで吸収する（ステップ2以降で実装）。
- **スコア列・累計列の数字**: セグメント表示風フォントのためPaddleOCRが安定しない
  （`0` が `-` に化ける、桁落ち等）。**スコアはOCRせず、順位から規定配点表で
  確定する方式に変更した**。表示される `+N` は常に順位の規定配点と一致するため
  情報量は変わらない。スコア列OCRは「読めた場合に限り配点と突き合わせる」
  クロスチェックとして残す。
- **累計の照合**: 累計点そのもののOCRは使わず、フェーズBの「名前の並び順」が
  自前の集計順位と一致するかで照合する（名前は読めるため）。累計点が読めた
  行だけ追加で突き合わせる。
